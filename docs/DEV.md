# מדריך מפתח — RACE_WEBAPP_LITE (מערכת תזמון והערכה לגיבוש)

מסמך התחלה למפתח חדש. גרסת **LITE** — בלי ESP32/RFID, הכל דרך הדפדפן.

## קישורים חיים
- כניסה: https://adart96.github.io/RACE_WEBAPP_LITE/
- אפליקציה (מפק״צ/מעריך): `/app.html` · לו״ז: `/schedule.html` · מפקד הגיבוש: `/commander.html` · פאנל מנהל: `/admin.html` · הקמת אירוע: `/event-setup.html`
- מוגש דרך **GitHub Pages מענף `master`** (path `/`). דחיפה ל-`master` = דיפלוי אוטומטי (~1–2 דק').

## סטאק
- **Frontend**: HTML/CSS/JS סטטי (ללא build). מודולי ES ב-`<script type="module">`.
- **Auth + DB**: Firebase (Authentication אימייל/סיסמה + Firestore). פרויקט `race-webapp-lite`.
- **סנכרון ל-Sheets**: Google Apps Script (`scripts/Code.gs`) פרוס כ-Web App; כותב ל-Google Sheets + Drive.

## מודל הנתונים (Firestore)
- `users/{uid}` — `name, email, role` (`admin|operator|evaluator|formation_commander`), `approved`, `team`, `sheetUrl`/`sheetFileId` (קובץ המעריך). ל־`formation_commander` אין צוות (`team: null`).
- `teams/{teamNumber}` — מאגר התאימות הישן ותבניות התחנות. אירוע חדש אינו מצולם ממנו אוטומטית; המקור התפעולי הוא `events/{eventId}`.
- `teams/{teamNumber}.rosterSource` — מקור רשימת המועמדים הישן: `type`,‏ `sourceId`,‏ `fileName`,‏ `importedAt`,‏ `importedBy`. באירועים חדשים `candidate-roster-import.js` ו־`event-setup-page.js` ממפים Excel/CSV לחוזה הקנוני ושומרים דרך `event-setup-repository.js`.
- `settings/commentTags` — תיוגי הערות כלליות.
- `settings/stationTypes` — `{ types: {...} }` — עריכות המנהל לסוגי התחנות (דורס את ברירת המחדל שב-station-types.js).
- `races/{race_event_team_station_round}` — סבב משותף ובטוח: `eventId, team, station, round, status, startedAt, startedBy, endedAt?, endedBy?, endedReason?, timeLimitSeconds`, צילום הרשימה `participantIds`,‏ `evaluationSchemaVersion: 2`, ו-`tags: []` ריק. אין בו ציונים, הערות או מדידות של מעריכים.
- `races/{raceId}/evaluatorAssessments/{evaluatorUid}` — הערכה פרטית למעריך ולסבב: `entries[participantId] = { scores, measurement, comments }`,‏ `schemaVersion`,‏ `createdAt`,‏ `updatedAt`. רק בעל ה-UID ומנהל יכולים לקרוא; מעריך אחר ומפק״צ אינם יכולים לקרוא גם דרך Firestore ישירות.
  `scores` משתמש במזהי תכונה יציבים (`resilience`,‏ `activity`,‏ `social_intelligence`,‏ `assertiveness`,‏ `analysis_judgment`) ולא בשם התצוגה הניתן לעריכה.
- `races/{raceId}/evaluatorArrivals/{evaluatorUid}` — סדר הגעה אישי למעריך: `participantIds`,‏ `order`,‏ `slotTimes`,‏ `completedAt?`,‏ `createdAt`,‏ `updatedAt`,‏ `schemaVersion`,‏ `revision?`.
  `order` מחבר משתתף למקום; `slotTimes[place]` מחבר זמן לחריץ המקום. לכן סידור מחדש משנה רק את `order`, והזמן נשאר עם המקום.
  `place`/`finishedAt` ישנים בתוך `tags` נשמרים לקריאה וליצירת נקודת התחלה אישית בסבבים מהגרסה הישנה, אך קוד חדש אינו כותב אליהם.
- `general_notes/{team_participant}/authors/{uid}` — ההערות הכלליות של כותב אחד בלבד. מפק״צ ומעריך קוראים וכותבים רק את המסמך שלהם.
- `privacy_migration_archive/{sourceId}` — עותק מנהל של שדות המקור הישנים לפני ניקוי; אינו חשוף למשתמשי התחנות.
- `settings/evaluationPrivacy` — סמן הסבה. רק `status: "complete", schemaVersion: 2` מפעיל את האכיפה המחמירה על מסמכים ישנים.
- `issue_reports/{reportId}` — דיווח תפעולי המשויך ל־`eventId`: זהות/צוות המדווח, קטגוריה ותיאור, הקשר תחנה/סבב, גרסת לקוח ומידע דיאגנוסטי מצומצם. אין בו ציונים, הערות הערכה או מספרי משתתפים. משתמש מאושר יכול רק ליצור; מפקד הגיבוש קורא את דיווחי האירוע הפעיל לצורך מרכז החריגות; מנהל בלבד מעדכן `status/adminNote`.
- `settings/activeEvent` — מצביע יחיד לאירוע הפעיל. `eventStaffingSchemaVersion: 1`
  מציין שהכניסה חייבת להיפתר מול `events/{eventId}/staff/{uid}`; באירועים ישנים ללא
  הסמן נשמרת תאימות ל־`users.role/team`.
- `events/{eventId}` — מטא־דאטה בלתי תלויה של אירוע: שם, מצב, מספר צוותים/מועמדים וגרסת סכימה.
- `events/{eventId}/teams/{team}` — צוות האירוע, רשימת מספרי המועמדים ומיפוי התחנות. מקור האמת לרשימת הצוותים, ללא תלות בקיום לו״ז.
- `events/{eventId}/candidates/{team_participant}` — ישות המועמד באירוע: `participantId, team, fullName, nationalId, emergencyContactPhone, doctorClearance, medicClearance`, המצב התפעולי (`active|withdrawn`), סיבת נשירה וגרסאות נפרדות לפרופיל ולמצב. מפק״צ ומעריך קוראים רק את מועמדי הצוות שלהם; מפקד הגיבוש קורא את כולם אך משנה רק מצב; מנהל בלבד רשאי לתקן פרופיל.
- `events/{eventId}/staff/{uid}` — מקור האמת לשיבוץ באירוע (`role`, `team`, `active`). באירוע סכימה חדש חוקי Firestore דורשים חברות פעילה זו; השדות הגלובליים ב־`users` הם הקרנה של האירוע הפעיל לצורכי ניתוב ותאימות.
- `events/{eventId}/artifacts/{id}` — manifest לקבצי Drive, המפריד בין מצב Firestore לבין side effect חיצוני ומאפשר retry בטוח.
- `events/{eventId}/dropoutRecommendations/{team_participant}` — המלצת מפק״צ יחידה למועמד, עם מצב `open|accepted|rejected|cancelled`. מפק״צ כותב רק בצוות שלו; מפקד הגיבוש פותר בלבד.
- `events/{eventId}/candidateStatusEvents/{id}` — יומן append-only של מעברי מצב. המסמך החדש והמצב החדש נכתבים באותה טרנזקציה.
- `events/{eventId}/schedule/master` — הגרסה המפורסמת של שיבוצי הצוותים: רשימת צוותים, שמות מפקדים שהוזנו ידנית ושורות מסודרות. שורה היא `global` לפעילות משותפת או `rotation` עם `assignments[team] = { stationId, routeNumber }`. מספר המסלול הוא מידע תפעולי נפרד ממספר התחנה באפליקציה.
- `events/{eventId}/schedule/draft` — סביבת העבודה היחידה של מנהל ומפקד הגיבוש. `baseRevision` קושר אותה לגרסה המפורסמת שעליה נבנתה ו־`draftRevision` מונע דריסה בין שני עורכים. שמירת טיוטה אינה משנה דבר אצל הצוותים.
- `events/{eventId}/teamSchedules/{team}` — הקרנה של טור צוות אחד מהגרסה המפורסמת בלבד. מפק״צ ומעריך קוראים רק את ההקרנה של הצוות שלהם ואינם מקבלים את מטריצת־העל.
- `events/{eventId}/scheduleRevisions/{revisionKey}` — צילום מלא ובלתי־ניתן לשינוי של כל פרסום, ללא שינוי של גרסאות היסטוריות. פרסום כותב את `master`, כל הקרנות הצוות, צילום היסטורי וטיוטה מסונכרנת באותה טרנזקציה. שחזור אינו מוחק עבר: הוא יוצר פרסום חדש מסוג `restore` שמצביע על גרסת מקור קיימת.

### חוזה ייבוא roster

#### תיקון שלמות הייבוא והפרדת ההכנה מההפעלה

- רשימת `events/{eventId}/teams` היא מקור האמת לצוותי האירוע. יצירת צוות ידנית אינה
  דורשת לו״ז; ייבוא מועמדים יוצר צוות חסר באותה טרנזקציה ששומרת את מועמדיו.
  ייבוא לו״ז יוצר את הצוותים החדשים והטיוטה באותה טרנזקציה. השמטת צוות מקובץ לו״ז
  אינה מוחקת צוות או מועמדים; צוות ללא שיבוץ מוצג כאזהרה.
- הכנת המועמדים אינה חסומה ללא לו״ז. הפעלה מחייבת לו״ז מפורסם, לא ריק ותקין
  ב־repository; גם Firestore מונע מעבר לאירוע פעיל ללא פרסום לא ריק.
- `fullName` הוא שדה השם הקנוני. נרמול רשומה ישנה משתמש ב־`firstName` כגיבוי;
  כתיבות חדשות למסמכי מועמד משמרות גם `firstName` כהקרנת תאימות זהה בלבד.
  אין להסיק שם משפחה משם מלא או לנהל שני ערכי שם נפרדים.
- המתאם מזהה שם מלא, או מחבר שם פרטי ומשפחה, ומכיר גם `מספר זהות`,
  `טלפון איש קשר`, `כשיר רופא`, `כשיר חובש`. כותרת כפולה/עמומה וערך לא תקין
  נדחים; לפני אישור מוצגים מיפוי העמודות, הכמויות ודוגמת נתונים.
- `providedFields` הוא מידע זמני של מתאם הייבוא ואינו נשמר ב־Firestore. עמודה
  חסרה או תא ריק משמרים מידע קיים. ערך `0` מפורש הוא עדכון מכוון לערך חסר.
  פרופיל חדש עדיין מקבל ברירות מחדל מטיפוס מתאים. רשומה חסרה אינה אישור רפואי.
- `events/{eventId}/rosterImports/{attemptId}` מתעד מצב ייבוא, מספר צוותים ומועמדים
  וקוד שגיאה מרשימה סגורה. אין בו שמות, תעודות זהות, טלפונים, שמות קבצים או טקסט
  חריגות חופשי. הצלחת קבוצת כתיבה נרשמת יחד עם הנתונים באותה טרנזקציה. תקלה
  ברשת יכולה למנוע גם שמירת כשל; רשומת `started` לבדה אינה הוכחת כישלון או הצלחה.
- יש לפרוס את הכללים לפני הפרונטאנד החדש; אין להוסיף `fullName` לנתוני ייצור לפני
  הפריסה, משום שהכללים הישנים דוחים שדות לא מוכרים. לאחר הפריסה יש לרענן לקוחות.

#### השלמת אירוע שנפגע מייבוא ישן

לפני ייבוא מתקן יש לגבות את מסמך האירוע, צוותיו ומועמדיו מחוץ לגיט ולבצע השוואה
עדכנית לפי `eventId + team + participantId`. אין להתאים לפי תעודת זהות חסרה.
ערך קיים שאינו חסר ושונה מהמקור דורש הכרעה, ולא דריסה אוטומטית. השלמת שם פרטי
לשם מלא מותרת רק אחרי אימות שהשם הפרטי תואם למקור. באירוע פעיל הייבוא מעדכן
שדות פרופיל בלבד ומוסיף חסרים; ציונים, הערות, סבבים, נשירות וגרסאות מצב נשמרים.
בדיקת הקובץ המקורי מול האירוע ב־5 באוקטובר 2026 מצאה 70 עדכונים ו־70 יצירות,
ללא מחיקות או סתירות. זו בדיקה, לא תיעוד של תיקון נתונים שכבר בוצע.

קובץ חיצוני אינו כותב ישירות ל־Firestore. מתאם האקסל ממפה כל שורה לשדות הקנוניים
`team, participantId, fullName, nationalId, emergencyContactPhone, doctorClearance, medicClearance`.
`buildCandidateRosterImport` מנרמל ומקבץ את שורות הקובץ. לפני כתיבה,
`event-roster-plan.js` טוען צילום אחד של צוותי האירוע ושל כל מועמדיו, בודק מגבלת 20,
מספרים, תעודות זהות, טלפונים, מצבי כשירות וכפילויות בכל האירוע, ומחשב רק את השינויים
הנדרשים. `event-setup-repository.js` שומר את התוכנית בטרנזקציה אטומית כאשר היא נכנסת
למגבלת Firestore, או בקבוצות של צוותים שלמים כשמחליפים טיוטה גדולה. `rosterRevision`
מונע משני ייבואים מקבילים לדרוס זה את זה; ניסיון חוזר עם אותו קובץ אינו משנה את רשימת המועמדים (נשמר רק רישום אבחון של הניסיון).
בטיוטה, צוות שמופיע בייבוא מוחלף במלואו; באירוע פעיל מועמדים קיימים אינם נמחקים והייבוא
מעדכן רק את שדות הפרופיל שלהם. צוות שלא מופיע נשאר ללא שינוי.
ה־adapter הוא המקום היחיד שמכיר שמות עמודות, sheet או פורמט קובץ מסוים.
ברשומה חדשה שדה חסר מנורמל ל־`0`: בשדות מחרוזת זהו `"0"`, ובכשירויות המספר `0`.
בייבוא לרשומה קיימת שדה שלא סופק נשמר כפי שהיה, ואינו מוחלף בברירת מחדל.
מספר מועמד חייב להיות מספרי ואינו יכול להיות `0`. יתר שדות הפרופיל יכולים להישאר
`0`; הם מוצגים כאזהרות מוכנות ואינם חוסמים הפעלת אירוע.

### ייבוא לו״ז ומועמדים

הדפדפן משתמש ב־SheetJS בגרסה מקובעת לקריאת הקובץ בלבד. `schedule-excel-adapter.js`
ו־`candidateRowsFromMatrix()` ממירים מטריצה לחוזים קנוניים ואינם מכירים Firestore.
השמירה ממשיכה דרך repositories הרגילים, ולכן ייבוא אינו מסלול עוקף ולידציה או הרשאות.
לו״ז דורש כותרות `תאריך`, `שעה`, `סוג`, `פעילות`, `צוות N`; תא תחנה בפורמט
`שם תחנה | מסלול`. אין להסיק משמעות מצבע, מיזוג תא או מיקום חזותי באקסל.

## סוגי תחנות והמדידה
17 סוגים, לכל אחד `measure`: `place` (סדר הגעה), `reps` (מדידה כמותית), או `none` (ציונים+הערות בלבד), ו-1–2 `params` (כל פרמטר → ציון 1–7).
- לכל סוג יש גם `intensity` תפעולי בטווח `0..3`. הוא משמש את הלו״ז בלבד ואינו חלק מההערכה או הייצוא. ל־17 הסוגים המובנים יש ערכי ברירת מחדל; סוג מותאם ללא ערך מקבל `0`. מנהל עורך את הערך בעורך סוגי התחנות.
- לתחנה עם `measure: "reps"` אפשר להגדיר `measureInput`: הערך `tap` (ברירת מחדל) מציג כפתורי ספירה; `manual` מציג רק שדה להזנת התוצאה הסופית. `ironNerves` (עצבים מברזל) מוגדר `manual`.
- ברירת המחדל ב-`js/station-types.js`. המנהל עורך ב-`settings/stationTypes` (פאנל → "עריכת סוגי תחנות").
- ה-app ממזג כל סוג שנשמר ב-Firestore עם ברירת המחדל. לכן הגדרה חדשה כמו `measureInput` נכנסת גם אם ב-Firestore קיים עותק ישן של התחנה. ה-sync שולח `params/measure/measure_label` ב-payload כך ש-**עריכות שמות פרמטרים/מדידה זורמות ל-Sheet בלי לגעת ב-Code.gs**. `STATION_TYPES` ב-Code.gs הוא fallback בלבד.

## זרימת סבבים והרשאות
- התפקיד הפנימי `operator` מוצג כ-**מפק״צ**. רק הוא מקבל בממשק כפתורי יצירה ועצירה. למנהל נשמרת הרשאת חירום ישירה ב-Firestore, אך `app.html` אינו מציג לו בקרי זמן.
- התפקיד `formation_commander` הוא תפקיד גלובלי ונפרד. הוא מופנה רק ל־`commander.html`, אינו שולט בשעוני תחנות ואינו נחשב מעריך או מנהל.
- מעריכים מקבלים את כל הסבבים בזמן אמת משאילת `races` ואינם יכולים לשנות שדות חיים/זמן.
- טאבים נגללים של סבבים מוצגים **רק** כאשר סוג התחנה הוא `sprints` או `stretcher` (ספרינטים/אלונקה).
- המפק״צ תמיד נשאר בסבב האחרון. מעריך רשאי לעבור בין הטאבים; ציונים, הערות, סימון סדר הגעה ושינוי הסדר זמינים גם אחרי עצירה ובסבב היסטורי. ספירה בלחיצה נשארת זמינה רק בסבב הפעיל; מדידה ידנית זמינה גם בסיום התחנה.
- בספרינטים ובאלונקה לכל מעריך יש סדר הגעה נפרד. שני מעריכים אינם קוראים או כותבים את אותו מסמך סדר, וחוקי Firestore מאפשרים למעריך לכתוב רק למסמך שה-ID שלו הוא ה-UID שלו.
- ציונים, מדידות והערות תחנה נפרדים באותה רמה: כל מעריך רואה ומעדכן רק את `evaluatorAssessments/{uid}` שלו. מפק״צ אינו רואה ציונים או תוצאות הערכה; הוא רואה רק את ההערות הכלליות שלו.
- בתפריט העליון קיים דף **מועמדים**. מעריך רואה בו ממוצע אישי לכל תכונה (ממוצע סבבים בתוך תחנה, ואז משקל שווה לכל תחנה), לשוניות תחנה, גרף מקומות ועריכת נתוני המקור גם בהיסטוריה. נתון חסר אינו נחשב `0`. מפק״צ רואה בדף רק את ההערות שלו.
- שם מלא, תעודת זהות, טלפון איש קשר חירום וכשירויות מוצגים בדף המועמד ובדשבורד מפקד הגיבוש בלבד. גרידי דירוג, ספירה, הערות תחנה וסדר הגעה ממשיכים לקבל ולהציג מספר מועמד בלבד. פרטי הפרופיל אינם נכתבים למסמכי `races`, להערכות, לסדרי הגעה, לדיווחי תקלה או לשורות סנכרון התחנה.
- בדשבורד מפקד הגיבוש שורת צוות נפתחת לרשימת כל מועמדי הצוות. הרשימה מציגה מספר, שם ומצב בלבד; זהות, טלפון וכשירויות נפתחים רק בלחיצה מפורשת על המועמד. החיפוש המשותף מקבל את אותו snapshot ומדרג התאמות מלאות/תחילית/חלקיות לפי מספר מועמד, שם או תעודת זהות; הערך `0` אינו הופך לתוצאת חיפוש.
- מרכז החריגות משתמש ב־`formation-alerts-model.js` ומקבל רק snapshots תפעוליים: סבבים מקבילים, סבב שהגיע לתקרת זמן, שיבוץ חסר במשבצת המפורסמת, פרופיל מועמד חסר, המלצות נשירה ודיווחי תקלה פתוחים. הוא אינו קורא הערכות, סדרי הגעה או הערות פרטיות.
- גריד סימון ההגעה בנוי תמיד מצילום המשתתפים המלא בסדר קבוע. אחרי סימון הכפתור נעלם חזותית, אך התא שלו נשאר שמור וריק ולכן יתר המספרים אינם זזים; בסבב חדש כולם מופיעים מחדש.
- כל חישובי הזמן עוברים דרך `session-policy.js` ונחתכים ל־40 דקות גם אם הטאב היה ברקע או לא היה מפק״צ מחובר. מפק״צ מחובר משלים אטומית את המעבר ל־`stopped` עם `endedReason: "time_limit"`; גם לפני שהכתיבה הושלמה, הלקוח מתייחס לסבב כאילו נעצר.
- זמן סימון נכתב פנימית כ-`serverTimestamp` לפי המקום ונשמר עד 40 דקות לצורכי מחקר וייצוא בלבד. זמני הגעה אישיים אינם מוצגים באפליקציה או בפאנל המנהל. ספירה בלחיצה נעצרת בתקרה; סדר הגעה, הערכה והזנה ידנית נשארים ניתנים לתיקון.
- שינויי הערכה פרטית ושינויי סדר אישי מתבצעים בטרנזקציות. `arrival-repository.js` משמש גם את מסך התחנה וגם את עמוד המועמד; שינוי סדר דורש התאמת `revision` שנצפתה, כדי למנוע דריסה בין שני מכשירים של אותו מעריך. שינוי של מעריך אחר נשמר במסמך אחר.
- `arrival-controller.js` מחזיק תור סימונים לפי סדר הלחיצות, נפרד לכל סבב ולזהות המשתמש שנלכדה ביצירת המאגר. התצוגה היא המצב המאושר בתוספת סימונים ממתינים, ולכן הכפתור נעלם מיד בלי להמתין ל־snapshot ובלי להזיז תאים. סימון כפול הוא פעולה ללא שינוי. `revision` עולה באותה טרנזקציה; אישור ישן לא מחליף snapshot חדש, ו־snapshot באותה גרסה יכול להשלים timestamps. snapshots מקומיים/מהמטמון אינם אישור שמירה.
- שגיאת סימון עוצרת את התור ומציגה ניסיון חוזר; אין דילוג אוטומטי על מועמד שנכשל. לאחר שגיאת שינוי סדר טוענים שוב לפני בחירה חדשה, ולא משחזרים אוטומטית סידור ישן. מעבר בין סבבים באותו דף משאיר כתיבות ממתינות קשורות לסבב המקורי. התור בזיכרון בלבד: אין הבטחת שמירה offline או לאחר סגירת דף. לפני סגירה יש אזהרת דפדפן, ובניווט פנימי לעמוד אחר/התנתקות יש חסימה כל עוד ממתינים סימונים.
- מעריך בוחר את הסבב האחרון רק בכניסה ראשונה להקשר תחנה/צוות (או אם הסבב שנבחר נמחק). סבב חדש אינו מעביר אותו אוטומטית, גם אם צפה באחרון עד אז. הלשוניות והודעת סבב חדש מתעדכנות גם כשהסבב החדש כבר נעצר; גלילה לסבב נבחר נעשית רק כשהבחירה משתנה. המפק״צ ממשיך לשלוט בסבב האחרון.
- גרירת סדר הגעה לוכדת את המצביע ברכיב הרשימה הקבוע, ולא בידית שבתוך השורה המוזזת. מאזיני תנועה/שחרור על המסמך מונעים תלות ביעד שמתנתק בעת `insertBefore`. אובדן capture של הרשימה, `pointercancel`,‏ Escape, הסתרת הטאב או יציאה מהחלון מבטלים את התצוגה המקדימה ומשחררים מאזינים ונעילה, בלי לשמור שינוי חלקי. שחרור תקין שומר פעם אחת עם גרסת המסמך שנצפתה בתחילת הגרירה. `tests/arrival-drag.unit.test.js` מכסה אובדן capture בעקבות הזזת שורה, ביטולים, מגע וריבוי מצביעים.

- כל שורה בסדר ההגעה ניתנת לגרירה: מ״טרם הגיעו״ למקום ברשימה, בין מקומות, ובחזרה לאזור האפור לביטול הגעה. אזורי הנחה נשארים גם כשהרשימה ריקה או מלאה. כפתורי `+`,‏ `×` והחצים נותנים חלופה ללא גרירה. לאחר סף תנועה של 6px מוצג עותק חזותי לא־אינטראקטיבי שעוקב אחרי המצביע באמצעות `transform`; השורה המקורית מסמנת את מקום ההנחה. העותק וכל המאזינים מוסרים בכל מסלול סיום/ביטול.
- הוספה למקום או ביטול משתמשים בפקודת `place` אחת, בטרנזקציה אחת עם `expectedRevision`; אין ״הוסף ואז סדר״. בזמן שמירה לא מתחילה עריכה נוספת, וכשל טוען מצב עדכני בלי לשחזר כוונת עריכה ישנה. הזמנים נשארים צמודים למקומות: הוספה מקצה זמן רק למקום האחרון החדש, וביטול מסיר רק את זמן המקום האחרון שהתפנה ומנקה `completedAt`. הוספה חוזרת יוצרת זמן חדש למקום שהתמלא, בלי לשייך זמני עבר לאדם. גם בסבבים היסטוריים החוזה זהה; זמני מחקר עדיין מסוננים לפי תקרת הזמן הקיימת ולא מוצגים למעריך.
- סבב חדש שומר צילום `participantIds`, ולכן עריכה מאוחרת של הצוות אינה משנה את ההיסטוריה. בסבב ישן ללא צילום משתמשים ברשימת הצוות ובנתוני ה-`tags` הישנים; הכתיבה הראשונה יוצרת עותק אישי בלי למחוק את המקור.
- לפני יצירת סבב חדש הטרנזקציה קוראת את מצבי כל מועמדי הצוות ומסירה רק `withdrawn`. נשירה באמצע סבב אינה משנה את צילום הסבב שכבר נוצר, ולכן אין מחיקה או שינוי היסטורי מפתיע.
- מפק״צ שולח המלצת נשירה מתוך דף המועמד. מפקד הגיבוש מאשר/דוחה בדשבורד או משנה מצב ישירות. הסיבות הסגורות הן `voluntary` (פרישה), `medical` (רפואי), `dismissal` (הדחה).
- חוקי Firestore מאפשרים למפקד הגיבוש לקרוא רק מסמכי תפעול וסבבי סכימה 2 באירוע הפעיל. תתי־המסמכים `evaluatorAssessments`,‏ `evaluatorArrivals` והערות פרטיות נשארים חסומים גם אם ניגשים אליהם ישירות.
- מנהל ומפקד הגיבוש עורכים **טיוטת** לו״ז, יכולים לשמור אותה בלי להשפיע על הצוותים, לצפות בכל טור צוות, ואז לפרסם במפורש. היסטוריית הפרסומים ניתנת לשחזור; השחזור יוצר גרסה חדשה ואינו משנה צילום ישן. שמות מפקדי הצוותים הם טקסט ידני לתצוגה בלבד ואינם מחוברים לחשבונות או להרשאות. לחיצה שלהם על תחנה פותחת את הרכיב המשותף `station-operational-dialog`: מצב, סבב פעיל/אחרון ומניין סבבים בלבד, בלי ציונים, סדר הגעה, הערות או בקרי זמן. אותו חישוב `station-operational-status` משמש את דשבורד המפקד ואת הלו״ז, כולל תקרת 40 הדקות ואזהרת סבבים מקבילים. אנשי צוות נכנסים ל״לו״ז צוותי״ מהתפריט ורואים רשימה אנכית מותאמת לטלפון; רק אצלם לחיצה על תחנה פותחת את מסך העבודה, ופעילות משותפת אינה קישור.
- בפתיחת `app.html` תחנת ברירת המחדל נבחרת לפי: יעד מפורש בקישור, סבב צוותי שכבר רץ, תחנת הלו״ז הנוכחית (או הקרובה), בחירה אחרונה, התחנה הראשונה. זו המלצה חד־פעמית בכניסה; שינוי ידני אחר כך אינו נדרס מעדכון לו״ז.
- עצימות התחנה היא מידע תיאורי בלבד. אין חישוב עומס מצטבר, אזהרות עומס או דרישה לסיבת חריגה. גרסאות לו״ז ישנות נשארות קריאות וניתנות לשחזור, בלי להחזיר את המדיניות שבוטלה.
- `firestore.rules` הוא מקור האמת להרשאות. חובה לפרסם אותו בקונסול ביחד עם הפרונטאנד.

### פריסת עדכון סדר ההגעה ויכולת חזרה

- `schemaVersion` נשאר 1. מסמך ללא `revision` נקרא כגרסה 0; הכתיבה החדשה הראשונה יוצרת גרסה 1, ואחריה כל שינוי חייב להעלות בדיוק ב־1, גם למנהל. מסמכים ישנים אינם דורשים הסבה גורפת.
- לפרסם את חוקי Firestore לפני ממשק המשתמש. לקוח ישן יכול להמשיך לכתוב למסמך ישן, אך אינו רשאי למחוק/לאפס גרסה במסמך ששודרג. יש לרענן לשוניות ישנות לפני תחילת עבודה; הרשאה נדחית בלקוח ישן עדיפה על דריסת הנתונים.
- חזרה לגרסת ממשק מלפני החוזה הזה אינה rollback תואם למסמכים שכבר שודרגו. אין להסיר את הגנת הגרסאות כדי לאפשר לקוח ישן; לתקן קדימה או לשמר את חוזה המאגר החדש בגרסת החזרה. ההיסטוריה ב־Git לבדה אינה משחזרת נתוני Firestore.
- בדיקות החוזה: `tests/arrival-controller.unit.test.js`,‏ `tests/round-navigation.unit.test.js`,‏ `tests/arrival-app.unit.test.js`, ובדיקות המאגר/הרשאות בתוך `tests/firestore.rules.test.js`. בדיקות התצוגה מריצות את פונקציות הממשק האמיתיות מול DOM מדומה; עדיין נדרשת בדיקת מגע חזותית במכשיר לפני פרסום.

## מבנה הפלט ב-Google Sheets
- **קובץ נפרד לכל צוות**, ובתוכו **טאב לכל תחנה** (כמו בקובץ "תוצאות"): שורה לכל (מועמד × סבב × מעריך), ממוין לפי סבב ואז מקום. הערות כלליות בטאב "הערות כלליות".
- **קובץ אישי לכל מעריך** — **טאב לכל מועמד**: שורה לכל (תחנה × סבב), רק ההערכות שלו.
- הקובץ הראשי (`SHEET_ID`) מחזיק רק **רישומים**: "קבצי צוותים", "קבצי מעריכים".
- לכל אירוע תיקייה נפרדת ששמה כולל גם את `eventId`; בתוכה תיקיות צוותים ומעריכים.
- טבלאות הרישום כוללות `Event ID`. חיפוש קובץ משתמש במפתח `(eventId, team)` או
  `(eventId, uid)` ולא בשם בלבד. שורות רישום ישנות בלי Event ID נשארות לשימוש לקוחות ישנים בלבד.

### יצירת קבצים — ממסך הקמת האירוע
כל הקבצים מוקצים **מראש** בשלב האחרון של `event-setup.html`
(`ensure_team_sheet` / `ensure_evaluator_sheet`) ורק לצוותים ולמעריכים ששויכו לאירוע.
נתיב הסנכרון (`handleRaceRow_`, `handleGeneralNote_`) **לא יוצר קבצים לעולם** — הוא מחפש
ברישום וכותב, וקובץ חסר מחזיר שגיאה מפורשת.

זה לא סגנון אלא תיקון באג: כשהיצירה ישבה בנתיב החם, כל כשל של `DriveApp` (הרשאה
חסרה, מכסה, תקלה זמנית) התפרש כ"הקובץ לא קיים" וייצר קובץ צוות חדש **בכל שורה** —
עשרות קבצים כפולים לכל צוות. `fileState_` מחליפה את `fileAlive_` ומבדילה בין
`alive`/`trashed`/`missing` לבין שגיאה אמיתית, שנזרקת במקום להתחזות ל"לא קיים".

לבדיקת המצב בפועל: פאנל מנהל → "קבצי Google Sheets" → **בדיקת קבצים**
(`type: "audit_files"`, קריאה בלבד) — מדווח כפילויות וכמה נתונים יש בכל קובץ.

## דיפלוי
1. **Firestore Rules + Indexes** — בפריסה שמוסיפה שדות/collections חדשים, לפרסם קודם את `firestore.rules` ואת `firestore.indexes.json`. דרך CLI: `firebase deploy --only firestore:rules,firestore:indexes`. אם מפרסמים כללים בקונסול, יש ליצור גם את האינדקסים המורכבים המוגדרים בקובץ לפני פרסום הפרונטאנד.
2. **Frontend** — merge/push ל-`master` → GitHub Pages מתעדכן. תמיד `Ctrl+Shift+R` בבדיקה (קאש).
3. **בהשקת סכמת פרטיות 2 בלבד:** אחרי שה-rules וה-frontend החדשים חיים, להיכנס לפאנל המנהל בזמן שאין פעילות בתחנות וללחוץ **"הפעל הסבה"**. הפעולה ניתנת לחידוש: כל מקור נשמר קודם בארכיון, רשומות שכבר הוסבו מדולגות, וסמן האכיפה נכתב רק לאחר הצלחה מלאה. אין ליצור את `settings/evaluationPrivacy` ידנית.
   הערה ישנה שאין בה `authorUid` נשמרת בארכיון אך אינה משויכת למשתמש, משום שאין דרך אמינה לדעת מי כתב אותה.
4. **Code.gs** — עורכים ב-[script.google.com](https://script.google.com) → מדביקים את `scripts/Code.gs` →
   **Deploy → Manage deployments → ✏️ → New version → Deploy** (שומר על אותה כתובת).
   - שינוי ב-Code.gs **לא** חי עד פריסה מחדש.
   - אם נוצרת פריסה חדשה עם **כתובת חדשה** — לעדכן `sheetsApiUrl` ב-`firebase-config.js` ולמזג ל-master.
   - פעם ראשונה: לאשר הרשאת **Google Drive** (יצירת קבצים/תיקיות).
   - בפריסה הנכונה `doGet` מחזיר feature בשם `event_scoped_files`. מסך הקמת האירוע
     מסרב ליצור קבצים אם ה־feature חסר, כדי לא לכתוב לרישום הישן בטעות.
   - **לפני כל אירוע**: מסך הקמת אירוע → "צור/בדוק קבצי אירוע". כשל הוא אזהרה
     עם אפשרות retry; הוא אינו חוסם הפעלה ואינו מוחק קובץ קיים.
5. **Firebase** — קונפיג ב-`firebase-config.js`. מפתחות ה-client ציבוריים (אבטחה דרך Firestore rules + Authorized domains).
6. **אירוע** — מנהל יוצר טיוטה ב־`event-setup.html`, שומר לו״ז וצוותים, מייבא או
   עורך מועמדים, משבץ סגל, בודק קבצים ומפעיל. רק ההפעלה משנה את `settings/activeEvent`.
   פרטי מועמד וסגל חסרים מוצגים כאזהרות בלבד; שגיאת מבנה בלו״ז או במספר מועמד חוסמת.

## בדיקות אוטומטיות
```bash
npm ci
npm test
```
`test:static` מפרש את כל קובצי ה־HTML, בודק מזהים כפולים והפניות מקומיות ומריץ בדיקת תחביר לכל מודולי ה־JS. `test:unit` בודק בין השאר את מדיניות הזמן, תהליך סדר ההגעה, חיפוש מועמדים, מרכז החריגות, טיוטה/פרסום/שחזור, מודל הנשירה, סכימת הדיווח ובחירת תחנת הפתיחה. `test:rules` מעלה Firestore Emulator זמני ומוכיח גם הפרדת הערכות, הרשאות זמן, בידוד הקרנות צוות, שמירת טיוטה ללא שינוי לצוותים, פרסום אטומי והיסטוריה בלתי־ניתנת לשכתוב. GitHub Actions מריץ `npm ci && npm test` ב־Node 22 וב־Java 21 בכל PR ובכל push ל־`master`.

## עבודה במקביל
- ענף לכל שינוי; מיזוג ל-`master` דרך PR או תיאום. **לא דוחפים ישירות ל-master בלי בדיקה** — הוא האתר החי.
- לא לשכוח: `firebase-config.js` משותף — שינוי כתובת Apps Script משפיע על כולם.
- אחרי שינוי ב-`Code.gs` — לפרוס מחדש, אחרת הסנכרון לא מתעדכן.
